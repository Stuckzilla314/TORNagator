## 2024-05-24 - Accessible Submit Button Patterns
**Learning:** For inputs like an API key that strictly require validation (e.g. exactly 16 characters), dynamically setting the disabled attribute on the submit button alongside conditional visual styling (e.g. a disabled background color and not-allowed cursor) provides immediate, intuitive feedback to users, preventing premature form submissions. It is also crucial to make sure screen reader labels use proper visually hidden CSS (`position: absolute`, `width: 1px`, etc.) rather than `display: none` which breaks accessibility.
**Action:** Apply dynamic disabled states on submit actions when form conditions are known upfront, and ensure labels are correctly hidden for accessibility.

## 2024-05-25 - Accessible Semantic Tab Pattern
**Learning:** In React, interactive tabs implemented as `<div>` elements natively lack essential accessibility features like keyboard focusability (tabbing) and predictable screen reader interaction. While `role="button"` and `tabIndex="0"` can be added, replacing non-semantic `<div>` tabs with native semantic `<button>` tags naturally provides these features. When refactoring components built this way, style resets (`background: 'none'`, `fontFamily: 'inherit'`, `fontSize: 'inherit'`, and overriding individual borders like `borderTop: 'none'`) can perfectly preserve the intended visual appearance while granting native accessibility improvements.
**Action:** When finding tabs built with non-semantic `div` elements, convert them to `<button>` tags and apply individual border style resets instead of `border: 'none'` to avoid React duplicate key errors if the component maintains a specific border (e.g. `borderBottom`).
